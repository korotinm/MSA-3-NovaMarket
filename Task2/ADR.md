### <a name="_qmphm5d6rvi3"></a>**Решение**
Решение по функционалу "История покупок" приведена в диаграмме [C4_Container.puml](C4_Container.puml).

Изменения в подсистемах, данные которых необходимы для формирования истории покупок, регистрируются в топиках кафка.
Подсистема Истории Покупок объединяет данные нескольких топиков по идентификатору заказа. Идентификатор заказа выбран, так как
событие Заказ является отправной точкой для череды действий которые приводят заказ в конечное состояние, а именно действия связанные
с платежной подсистемой, логистикой и непосредственно самим заказом.

В данном решении используется EDA и CQRS. Было решено, что схема для просмотра истории заказов должна быть модифицирована
под заявленные требования в задании, поэтому была выделена подсистема Истории Покупок с воркером объединяющим данные из топиков, из разных подсистем,
с дальнейшим наполнением хранилища со своей схемой хранения.

Для реализации реактивной системы и в дальнейшем масштабируемой под любые нагрузки - была выбрана Kafka как канал доставки событий до подсистемы.
Для снятия нагрузки с подсистем заказов, платежной и логистической - выбран паттерн CQRS для формирования собственной схемы хранения - для чтения покупателями.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

#### Альтернатива I:
В качестве альтернативы можно было рассмотреть реализацию системы используя паттерн API Composition и использовать
подсистемы платежную, логистическую и заказов как источники данных, но такое решение будет влиять на подсистемы - их производительность.
Этот же подход с комбинацией CQRS мог бы разгрузить подсистемы и сформировать отдельный источник для чтения исторических данных по заказам. 
Но это решение не универсально, так как новые подсистемы подключить сложней и даже невозможно, так как для более простого подключения понадобилось бы внедрять EDA,
а именно Kafka как персистентное хранилище для обработки разными подсистемами.

Чтобы не городить "бутерброд" из подходов и паттернов, был выбран проверенный способ - EDA + CQRS как основное решение.
Данное решение позволит в будущем переиспользовать данные из Kafka в других подсистемах: аналитических, ML и др.


#### Альтернатива II:
Event Sourcing не стал рассматривать, так как данный подход подошел бы больше для платежной подсистемы.
Для просмотра истории платежей, а точней цепочки изменения платежей со временем.

**Недостатки, ограничения, риски**

Высокая стоимость решения.
Работа с Kafka - сложно, поэтому требуются соответствующие компетенции от команды.

Выделение функционала истории заказов в отдельную подсистему делает функционал оторванным от систем первоисточников.
Риск, того что в истории заказов будет товар который не существует в сервисе Товаров, существует.
Но для этого в подсистеме История Заказов данные долджны быть самодостаточными и полными, что конечно требует больших дисковых объемов для хранения истории и для горячего хранения больше RAM.

Так же есть риск потерять данные в Kafka кластере при аварии, поэтому кластер должен быть построен по лучшим практика и быть распределенным по нескольким датацентрам.
Должна быть настроена репликация топиков и предусмотрен длительны Retention Policy для исклбчения риска удаления не обработанных данных подсистемами.
